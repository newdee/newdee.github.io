Cloudflare Computer 的文件存储与执行后端

2026-08-10 ·笔记 ·2631 字 ·约 7 分钟 ·阅读 次
CloudflareDurable ObjectsFUSE

Cloudflare Computer 将持久文件系统放在 Durable Object 的 SQLite 中，容器与 Dynamic Worker 作为可选择的执行后端。
执行环境可以重建，文件的权威副本留在工作区；容器后端需要增量同步，Worker 后端则直接通过 RPC 访问文件。
本文按预览版本的存储、同步和执行生命周期说明，文档中的前瞻设计单独标出。

项目范围

@cloudflare/computer 是一个跑在 Durable Object 里的虚拟文件系统：整棵树落在 DO 自带的 SQLite 里，
对外是 workspace.fs（用起来像 node:fs/promises）加 workspace.runtime.exec(source, { backend }) 一个执行入口。

今天有三种后端：container（真容器加 FUSE 挂载）、isolate shell（Dynamic Worker 里跑 just-bash）、isolate JavaScript（Dynamic Worker 里求值 ES module）。
也可以一个后端都不配，纯当持久文件系统用——fs 照常工作，exec 才抛错。

项目注明 PREVIEW ONLY，API 不稳定，不适合生产；docs/ 下二十篇规格自称 forward-looking，要当设计意图读，不能当代码现状读。
下文尽量把两者分开标：比如 R2 只读挂载在 schema 里留好了座位（_vfs_mounts 表、stub_size 列），但运行时还没接线，就属于「规格意图」。

状态归属

给 agent 配环境，常规做法是发一个容器：文件在容器盘上，跑完要么整包丢弃，要么自己往对象存储打包搬运。
若将文件权威副本放在临时执行环境中，回收前就需要另行保存。Worker isolate 的持久化也需要外部存储，因此执行生命周期与文件生命周期应分别设计。

这个项目把关系倒过来：权威态只有一份，住在 DO 的 SQLite 里（DO 本来就是带事务的有状态单点），
执行后端以稳定 ID 注册，首次使用时建立连接。容器重启或 isolate 回收后，可以从持久工作区重新接入；执行进程本身的状态则需要按后端能力分别处理。

持久化结构

持久层采用 inode 与目录项分离的结构。vfs_dirents 将 (parent_inode, name) 映射到 child_inode，vfs_nodes 保存节点属性，多个名字可以指向同一 inode。本地改名修改目录项，不必搬运文件内容。

文件按 512 KiB 分块，内容哈希作为 vfs_blobs 的寻址键，重复块可共享。节点冗余保存 size，因此 stat 不需要每次对所有块求和。

vfs_meta 的单调 rev 在每次变更时原子增加，并写到节点。Workspace 先将变更放进 FIFO 串行处理，使计数器和修改顺序一致；未来若增加并发写者，需要重新验证这一顺序约束。

节点的 rev 索引用于扫描指定游标之后的变化，增量同步不必重新比较整棵树。这里需要区分本地目录项修改与跨后端同步：后者可能因整棵子树路径变化产生更多记录。

同步协议

容器后端维护内存中的第二份 VFS，因此每次执行前 push，执行结束后 pull；两个 Worker 后端直接访问宿主文件系统，不需要这条同步回路。

push 按容器尚未见过的 rev 发送变化，同一路径的连续修改可合并为终态。条目携带块哈希而非完整字节，先以 hasObjects 查缺失块，再用 pushObjects 传输缺少的内容。

pull 通过 fetchChanges({ after }) 读取容器变化，游标为 (rev, path)。接收端每批处理 256 条：查缺失块、fetchObjects、applyChanges，完成后推进游标。中断后从最后提交批次继续，alreadyApplied 跳过重复记录，将重放范围限制在一批。

协议传输状态而非操作序列，不提供 rename 指令。改名表达为新路径存活记录和旧路径墓碑，所以接收端不必重放原始操作顺序；代价是目录改名需要为子树各路径生成更新。

类型冲突采用 last-writer-wins，接收的节点可能替换原有子树。硬链接也不跨后端保留身份：多个名字分别传输，目标端成为内容相同的独立文件。目录幂等判断只看 mode，不用 mtime，避免两端目录时间差反复触发同步。

容器后端

容器里跑的守护进程叫 computerd，是个 Node SEA 单二进制：Node 运行时、fuse-native 预编译件、libfuse 全部内嵌，
宿主镜像不需要装 Node，Debian slim 加个 fuse3 就能起。

它把容器内 VFS 用 FUSE 挂到 /workspace，容器里任何工具——shell、npm、编译器——看到的就是 DO 里那棵树，路径一致。
建连是反向拨号：后端调 computerd 的 POST /connect，让它主动拨一条 WebSocket 出来，capnweb 会话的 bootstrap stub 是 WorkspaceRPC（sync 与 shell 两个子 stub）。

容器侧 VFS 放在内存里，容器重启就丢，下一次 push 重新基线——权威态从来不在这一边。

命令执行的括号是固定的：push、spawn、流事件或 result、pull，把 result() 或事件流耗尽，收尾的 pull 才算完成。
computerd 自己的默认端口是 45678，Cloudflare 后端把镜像内监听钉在 8080；
它保留进程日志，断线后 getExec 能重新挂回去看回放、补信号——三个后端里生命周期最全的一个。

isolate shell

该后端在 env.LOADER 创建的 Dynamic Worker 中运行 just-bash。每个文件系统操作通过 Workers RPC 返回宿主 Durable Object，直接访问权威副本，结果中的 pushed 和 pulled 恒为零。

DurableObjectNamespace 不能直接经过 Worker Loader 环境的 structured clone，因此注入 WorkspaceServiceProxy，由宿主处理 env.HOST.getWorkspace()。isolate 的 globalOutbound 设为 null，不能直接 fetch 或 connect，只保留宿主代理入口。

内置 git 与 assets publish 通过受信转发执行，R2 绑定和签名密钥不直接进入 isolate。Shell 命令是 just-bash 支持的子集，包括 cat、grep、awk、sed、jq；依赖系统编译器、包管理或浏览器的任务需要选择容器后端。

Worker Loader 以 workspace-shell:${workspace.id} 缓存 isolate，同工作区并发执行共享热实例。该版本采用单次调用、缓冲结果，不保留供事后重挂的执行记录。timeoutMs 和并发 killExec 在语句边界协作停止，不能将其视为任意计算点可立即抢占。

isolate JavaScript

第三种后端把 source 当真正的 ES module 求值，也在 Dynamic Worker 里：

默认导出函数收到 options.input，返回值原样回到 result().value——这是结构化的值通道，不是 stdout 文本协议。
相对导入从 cwd 出发经权威文件系统解析，而且是先静态解析完整个模块图再起 Worker：拒绝符号链接穿越，
深度、模块数、总字节都有上限，动态 import 只认字符串字面量。

node:fs/promises 是 Workspace 后端的，isolate 里写文件就是写 DO 的 SQLite；ws:git、ws:artifacts 两个受信模块管提交与发布。

process 是个 shim：env 只是调用方传入的快照，DO 自己的绑定和密钥永不合并进来；stdin 是一次性异步迭代；argv、platform 给的是占位假值。
执行管理的默认限额为：默认并发 24，超了直接 EEXEC_BUSY；执行记录保留 100 条或 60 分钟，可回放；
取消先停新的宿主能力调用、等已受理的调用排空，然后才发布 exit 130——正常完成同样排空，不存在 exit 0 之后还有未落账的写。

有个容易踩的点：runtime.exec() 在 Dynamic Worker 跑完之前就返回，靠悬着的宿主调用把 DO 顶在内存里；
handle 拿了不读，DO 一闲置执行就可能被驱逐——要么把事件流排干，要么给必须活过驱逐的工作配 ctx.storage.setAlarm()。

使用

后端按子路径导入，不用的后端连带 just-bash 载荷一起被 tree-shake 掉。能做的事：

workspace.fs：mkdir、readFile、writeFile、rm、symlink、stat，全异步、绝对路径、跨 DO 重启持久；
workspace.runtime：exec、getExec、killExec、disposeExec，handle 既是事件流又能 result()；

命令后端的 result 带 pushed、pulled 和 sync 状态，命令成功而 pull 失败时可配 SyncRetryScheduler 只重试同步、不重跑命令；
@cloudflare/computer/tools：现成的 AI SDK 工具面（read、write、edit、ls，可选 exec 与 publish）；
R2 只读挂载：规格已写、schema 留座，运行时未接线（规格意图，非今日代码）。

省略 backend 就用第一个配置项。文档特意提醒：路由不是鉴权，公网网关要自己校验 backend 参数。
仓库的 8 个 examples 里，think-compare-runtimes 把同一个 agent 任务在容器和 worker 两种运行时上并排跑，最能看出取舍。

使用限制

工作区约 10 GB 上限，跟 DO 存储共享；容器侧整棵树在内存里，工作区容量与内存预算都需按实际文件规模评估，不能只按仓库类型判断。
FUSE 在大文件顺序 IO 上吃亏。官方 fs-bench 对 cloudflare/sandbox-sdk 做全量 npm install（854 个包、36675 个文件）：computerd 124.7 秒，容器 ext4 63.9 秒，tmpfs 34.3 秒，比真盘慢约一倍。

同一基准中的元数据操作耗时比为：stat 0.91x、rm 0.66x、mkdir 树 0.74x、find 0.72x、git init 加提交 0.72x——内存 inode 表的功劳。
大文件才是重灾区：纯读 64 MiB 比真盘慢 30 倍、copy 慢 40 倍；但 npm init 加小安装 0.95x 追平真盘，日常负载的大头本来就是元数据。

慢的根源在写路径每 512 KiB 就哈希一次进内容寻址库，换来的是按块增量同步和内容去重。

这些性能数值来自项目 fs-bench，受硬件、文件分布和缓存影响。它们说明元数据、小文件与大块顺序 IO 需要分开测，不能用单一安装任务代表所有工作区负载。

接入时先验证命令完成、同步完成和文件持久化这三个时点，尤其要处理命令成功但 pull 失败的情况。
