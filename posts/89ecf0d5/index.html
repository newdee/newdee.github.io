Skill Shelf：技能版本、任务路由与配置发布

2026-08-10 ·笔记 ·4682 字 ·约 12 分钟 ·阅读 次
RustAgentMCP配置中心

Skill Shelf 管理 Skill 目录包、提示词和服务配置，后端使用 Rust，Web 与 Tauri 桌面端共用 React 界面。
Skill 部分提供内容版本、搜索路由、反馈草稿和 MCP 读取；配置部分区分草稿与发布，并按 namespace 授权消费方。
这篇从存储模型讲到请求路由，再说明配置发布与权限，重点区分哪些状态可以编辑、何时开始对调用方生效。

起因

Skill 往往不止一段提示词，还包含脚本、参考资料和资源。修改后需要比较差异、回退和试验分支，调用时又需要按任务找到合适版本，因此内容版本和检索是两个独立需求。

服务配置也需要区分编辑与生效，并限制不同调用方能读取的范围。Skill Shelf 复用存储、身份和版本管理的部分机制，但两类内容有不同的发布与授权流程，不能把服务密钥按普通 Skill 文件分发。

早期的 prompt-shelf 只管理提示词，当前版本扩展为 Skill 目录包与配置中心。下面分别看共用基础和两条消费路径。

组件与部署形态

一个 Cargo workspace 三个 crate，加一个前端。

skill-shelf-core —— CAS 对象库、版本模型、SKILL.md 解析校验、Index trait。不依赖 HTTP，也不知道 UI 存在，可以脱离 server 单测
skill-shelf-server —— Axum REST、JWT 认证、两套配置（自身设置 + 配置中心）。唯一的后端
skill-shelf-mcp —— stdio MCP server，把 REST 包成 agent 能用的工具

app/ —— React 19 + Vite + TanStack + shadcn/ui，src-tauri 是纯壳

最早定下、后来证明最省事的一条决定是：前端只通过 HTTP 访问后端，桌面和 Web 走完全相同的代码路径。

Tauri 那层不内嵌 core，不用 invoke() 访问业务逻辑，只负责窗口、托盘、文件对话框，以及启动时把 server 二进制作为 sidecar 拉起来监听 127.0.0.1。桌面的离线能力来自「打包进壳的 server 二进制」，而不是把 core 编进 Tauri。

好处是前端只有一份 axios 客户端，base URL 运行期可配：

Web 存 localStorage，桌面存 Tauri Store，axios 用请求拦截器动态读当前 base URL。所以同一个构建产物既能当桌面壳里的本地客户端，也能填个远程地址连团队的服务器，改完即时生效不用重新构建。

如果当初让 Tauri 直接调 core，就会有两条代码路径、两套错误处理，Web 和桌面每次都要各自验一遍。这个决定省下的是持续的成本，不是一次性的。

版本管理

版本对象分为文件内容、目录快照、提交和分支：

Blob 保存文件字节，以内容哈希寻址。
Tree 保存有序的 path → blob 哈希 映射。
Commit 保存 tree、父提交、作者、说明与时间，自身内容哈希作为 ID。
Branch 是指向 head commit 的可变名称。

对象落在文件系统 CAS 中：

相同字节重复 put 不新增对象。修改 SKILL.md 时，新增其 blob、更新 tree 并产生 commit，未变文件继续引用原 blob。分支切换修改指针，不重复制整个目录。

关系数据库保存 skills、branches、feedback、users 和路由索引等可查询状态；不可变对象留在 DATA_DIR/objects。SQLite 与 Postgres 后端共用对象格式，但多实例还需要共享对象库，不能只换数据库连接。

Skill 与 prompt 通过 kind 区分。prompt 使用单文件内容，Skill 可以包含脚本和资源，两者共用对象版本，消费和校验规则则按类型处理。

元信息校验

按 Agent Skills 规范，SKILL.md 的 front matter 是名称、简介、许可与元信息的权威来源。导入及提交 kind=skill 时，服务端调用 core 的纯解析校验，缺少文件、front matter 非法或 name 与身份不符时返回明确的 4xx。

提交成功后，将元信息缓存到 skills 表并刷新路由索引，列表与预览由此避免反复读取对象文件。数据库中的字段是提交结果的投影，不能作为另一份独立可编辑来源。

解析位于 core::skillmd，校验时机由 server 决定，core 的通用 commit 不承担所有业务类型约束。调用其他入口时也应检查是否经过相应校验。

技能路由

路由信号就是每个 skill 的 name 加 description——Agent Skills 规范本来就约定 description 要写「什么时候用我」，这正是路由需要的东西。

调用方有两类意图，分别有接口：

精确取用 —— agent 明确知道要 pdf-parse，GET /skill/by-name/{name} 或 mode=exact 直取，不排序
模糊搜索 —— 给一句「帮我把 PDF 转成文本」，mode=fuzzy（默认）返回排序候选，加 rerank:true（或 mode=smart）启用 LLM 重排

向量的取舍

当前召回使用词法检索，没有维护向量索引，考虑的是描述长度、离线运行和更新成本：

SQLite FTS5 自带 bm25()，可以对名称和短描述进行离线召回，无需额外部署检索服务。召回效果取决于描述与查询是否共享词汇，应使用实际任务评估。

LLM 重排补得上语义。它只需要看 N 条短描述，几百 token 一次调用，就能处理「用词不同但意思相近」。重排只处理已召回候选，不能补回遗漏项。而且它复用了 refine 已有的 AI_* 配置，没引入任何新东西。

向量检索也有持续更新成本。向量检索需要管理嵌入模型、索引更新及模型变更后的重建；采用本地或外部服务时，部署与调用成本不同。是否值得承担这些成本，需要与词法召回遗漏造成的损失比较。

代价也得说清楚，不能只讲好处：LLM 只能从 BM25 召回的候选里选。 如果某个 skill 和 query 零词法重叠，BM25 根本没把它召回，LLM 也救不回来——这正是向量能补而这个方案不能的场景。

缓解手段两个，都在代码里：

skill 总数不超过 15 时直接跳过召回，全量交给 LLM 重排，候选覆盖全部 Skill。这里保证的是候选覆盖范围，不是最终选择正确率，也不能假定所有个人库都在这个规模。超过 15 才走 BM25 取 Top-20 再重排。

未配置 LLM 时只使用 BM25。所以三档能力是随配置逐级增强的，不是要么全有要么不可用。

分数范围

召回分数与数据库实现相关，接口需要保留这一差异。

档 A 的 score 来自 SQLite FTS5 内置的 bm25()，是 SQLite 算的，不是我实现的。而 skill_fts MATCH 和 bm25() 都是 SQLite 专有语法：

（bm25() 返回的是负值、越小越好，所以取回来要取反。）

换到 Postgres 就是另一套算法了：tsvector 加 ts_rank，不是 BM25；要真 BM25 得上 pg_search/ParadeDB 扩展。MySQL 又是 MATCH…AGAINST 自己的相关度。

结论有两层。对使用者：分数只在同一次查询内相对有意义，BM25 的 IDF 依赖语料规模，库小的时候绝对值噪声很大，界面上可能就显示成 0.0000；可靠的是排序，不是绝对分。对代码：召回必须抽象成可替换实现，每个后端一套（SqliteFtsRouter / PgFtsRouter），因为算法本就不同。

而 LLM 重排天然跨库——它只吃候选的 name 加 description，跟数据库无关。所以换后端只冲击召回层，重排层完全不用动。这个分界不是设计出来的，是被「分数不可移植」这个事实逼出来的。

顺带一个小地方：FTS5 的 MATCH 表达式不能直接拼用户输入，会被特殊字符搞出语法错误。处理是按非字母数字切词、每个词加引号、用 OR 连起来：

界面上有个路由测试台：输入需求，实时看命中哪些 skill、分数多少。调 description 的措辞时很有用——路由不准时，可以分别检查 description、分词召回和重排结果，不应把所有错误都归因于描述。

反馈闭环

反馈记录 rating（-1 / 0 / +1）、正文、source 与原始 query。source 区分人工意见和 Agent 自评，query 记录当时怎样路由到这个 Skill，便于分别分析内容问题与路由错误。

POST /skill/{id}/refine 读取当前版本和该版本尚未处理的 open 反馈，调用模型生成草稿。结果提交到 refine/* 分支，主分支保持不变，用户通过多文件 diff 审核后合并。

合并后重建该 Skill 的路由索引，并将采纳反馈标为 applied。后续 route 取得更新后的版本。反馈样本可整理成路由评测集，但人工与模型反馈应保留来源，不能默认当作同等可靠的标签。

Skill 包中可能包含 scripts/，因此审核既包括指令含义，也包括实际文件修改。草稿隔离提供复核机会，不会自动验证脚本安全。

MCP 接入

skill-shelf-mcp 以 stdio 运行，作为 REST 服务的 Agent 客户端，提供：

route 按任务描述找候选，list_skills 浏览、过滤与分页。
load_skill 读取 SKILL.md 及包内文件清单。
read_skill_file 按需读取脚本、参考等文件。
feedback 提交使用反馈，get_config 读取授权 namespace 的已发布合并配置。

正文与附件分开读取，使 Agent 可以先判断适用性，再加载实际需要的文件。工具返回内容是待使用数据，不能仅因来自技能服务就获得高于当前任务的指令权限。

配置工具从环境变量 SKILL_SHELF_CONFIG_TOKEN 读取 service token，内部转换为 X-Config-Token 调用 resolve。未设置时工具仍列出，但执行会明确报错；可读 namespace 由 token 的 grant 决定，MCP 复用服务端授权检查。

编辑与发布

一开始 namespace 就是个裸 KV，改完立刻生效。用了两天就发现不行：改配置和让改动对消费方生效，是两件应该分开的事。手滑改错一个值，线上服务下次重启就读到了。

现在每个 namespace 是 { draft, versions[] }：

编辑改草稿 —— PUT /config/namespace 只动 draft，resolve 完全不受影响
消费读已发布 —— resolve 返回 versions.last() 合并 _global 的已发布版
发布 —— publish 把 draft 快照成新版本，版本号单调递增；草稿和最新已发布相同则拒绝

回退 —— rollback 把某历史版本载回 draft，不直接发布，admin 复核后再 publish，也就是「回退了再发布」
diff —— 逐字段对比 draft 和已发布，added / removed / modified，secret 两侧都打码

回退先修改草稿，再经 publish 生效，使恢复历史版本也经过同一发布入口。

配置授权

service token 只存 SHA-256 哈希，明文只在签发时展示一次。每个 grant 记录能读哪些 namespace。

另一个是：关掉认证（不设 JWT_SECRET）时，整个 /config/* 拒绝服务。桌面自用场景下不设 JWT_SECRET 很方便，但配置中心必须例外——没有认证，攻击者就能自助签发一个 token 把所有 namespace 的明文读走。宁可让这个功能在开放模式下完全不可用。/config（自身设置，桌面自用）仍然开放。

还有一条已知限制，写在文档里没藏着：namespace 层的 null 语义是「从本层删除这个 key」，所以无法覆盖式屏蔽 _global 的某个 key——能覆盖值，暂时不能删。_global 会合并进每一次 resolve，任何有效 token 都读得到，所以那里只该放非敏感的共享默认值。

.env 导入

迁移现有服务时最烦的一步是把 .env 一行行敲进界面。所以做了导入：粘贴文本或选文件，前端解析（注释、export 前缀、引号转义都认），导入前逐 key 预览新增 / 覆盖 / 跳过 / 无效行，确认后合并进草稿——发布前不影响任何消费方。

值一律按字符串导入，不做类型猜测。PORT=8080 到底是数字还是字符串，猜错了比不猜更麻烦。

配置持久化

配置这种东西，写坏了比读不到严重得多。所以：

写操作是快照 - 落盘 - 提交内存三步，磁盘写失败则运行态完全不变并返回 500，不会出现「内存里改了、文件里没改」的状态。

加载时区分两种失败：文件不存在用默认值（首次启动的正常情况）；解析失败直接 panic 拒绝启动。宁可起不来，也绝不用空配置覆盖已有数据——如果解析失败时用了默认值，下一次任何写操作都会把用户的配置全部清掉。

旧的裸 {k:v} namespace 格式按「有没有 versions 键」识别，自动迁移成已发布的 v1，而且没加 deny_unknown_fields，未来新增字段不会让老数据加载失败。

一致性检查

对象版本、关系索引和配置发布有不同的一致性边界。内容提交生成不可变对象，数据库缓存元信息与路由结果；namespace 草稿则只有发布后才进入 resolve，历史版本回退也先落草稿。

路由中可共享的是候选数据和重排接口，数据库相关的是召回语法及分数。SQLite 的 BM25 与 Postgres 的 ts_rank 不能直接比较绝对值，应分别验证排序效果。

桌面与 Web 共用 HTTP 业务接口，降低重复实现，但桌面仍需测试 sidecar 启动、端口与退出处理，远程部署还需测试认证和网络失败。代码路径共用不能代替环境验证。

反馈驱动的 refine 只生成分支草稿，合并前检查文件差异。Skill 包含脚本，内容校验与用户审阅均不等于执行安全保证，还需要后续的供应链与沙箱验证。

待实现项

按价值排，最缺的还是「给 agent 消费」这条线上的东西：

skill 安全扫描 —— skill 含可执行脚本，导入外部 skill 前应该扫危险操作。这是供应链安全，目前完全没做，是我认为当前最大的缺口
skill 自检 —— 校验 SKILL.md 引用的 scripts/、相对链接是否真的存在；沙箱冒烟跑一下脚本
语义版本与发布通道 —— 现在只有 commit，没有 v1.2.0 这种 tag，也没有 latest / stable 通道

使用分析 —— 路由次数、命中率、反馈趋势，这些数据本该喂回「越用越好」的闭环，现在只有原始反馈
从 GitHub 仓库直接拉 skill —— 设计已经写好（下 zipball 复用现有 zip 导入通路），还没实现
CLI —— push / pull / search / route

另外 Postgres 那条路虽然跑通了 e2e，但 CAS 还在本地文件系统，多实例部署要先把对象库换成共享对象存储。
