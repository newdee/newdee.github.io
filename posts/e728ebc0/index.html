prime-agent，把大工程拆成七个阶段的编排器

2026-08-10 ·笔记 ·1957 字 ·约 5 分钟 ·阅读 次
AgentCursorTypeScript工作流

把一个大 feature 整个丢给 coding agent，得到的多半是一个几千行的 PR：类型、接口、实现搅在一块，审无可审，错了也说不清从哪一步开始错的。
prime-agent 的解法是把开发强拆成七个阶段：每阶段一份 markdown 合同、一次 commit、一个 PR 检查点，重点阶段再拉一个全新 agent 做对抗审查。它本体是跑在 Bun 上的终端小工具，驱动 Cursor 云端 agent 干活；从合同里的 prime@terminal.shop 和满篇 Odin 游戏路径看，应该就是 ThePrimeagen 自己每天在用的那套。
项目没有 README，这篇是通读源码后的笔记：合同怎么设计、流水线怎么转、断了怎么接。

七份合同

核心设计不在 TypeScript 里，在 phases/ 的七份 markdown 里。每份是一个阶段的行为边界加一张 done criteria 清单，七份合计 187 行，第一条永远是「先追平 master」。分工：

phase 1 侦查：读旧代码、挑或建 Linear 工单、写一页实现草稿，不写代码
phase 2 结构：只改 objects/ 下的类型定义。合同原话是不许 build——只做结构改动，按定义此刻就该有东西是坏的
phase 3 契约：只动函数签名、常量和模块级数据，新函数体一律 unreachable() 占位；改已有函数的签名可以，函数体一个字不许动
phase 4 接线点：在运行路径上给每个要改的位置打 TODO，理由限两行内，不写任何代码
phase 5 试写审计：完整实现一遍 feature，验证 2-4 的契约够不够用，缺口按 phase 2/3/4 归类上报，然后把试写代码整体回滚
phase 6 断言：补 phase 5 报出的缺口，给不可能状态加负空间断言（合同还让 agent 去参考 NASA 的断言指南）
phase 7 实现：填掉全部 TODO，端到端跑通，验收脚本 agent_task_finalize 必须过

这么拆的妙处是前四个阶段的 diff 都小而纯：只有类型、只有签名、只有 TODO 注释，人审起来几分钟一个。合同还把 Linear 工单当进度指针用：每阶段开工前先把工单挪到对应 Phase，流水线跑到哪，看板上一目了然。验收口径也定得很死：phase 5 和 7 都得用 JSON 驱动的 game 起一局验证 feature 真能跑，phase 7 的合同还明写不许拿录屏当证据。

最狠的一笔是 phase 5：花整整一轮做完整实现，唯一目的却是验证契约，做完即弃。听着奢侈，其实是笔明白账——agent 的算力时间不值钱，契约返工才值钱。真实现写到一半才发现 phase 2 少个字段，和在注定扔掉的试写里发现同一件事，修正成本差着数量级。

流水线

编排器是 phase-7.ts，388 行，一条串行流水线。从 phase 1 起步全程 13 步：7 个执行步、5 个审查步、1 个 phase 5 之后的补漏步（回头补 2-4 阶段的契约改动）。跑起来就是 bun phase-7.ts，敲一句 starting prompt，报完文件路径就可以去干别的，终端里只剩一个盲文小转轮在转。

每个阶段发给 agent 的任务提示词简单得过分，就一句 start phase N，随行的是两块内联上下文：该阶段合同的全文，加起跑时交互式指定的常驻文件。规矩全部长在合同里，代码不重复一遍。用户敲的那句 starting prompt 只有 phase 1 见得到（跟在 start 7 phase planning 后面），此后各阶段全凭合同和会话记忆推进。

起跑时它还会分两次问你要文件：一批随每个 phase 任务带上，一批只随审查带上——给审查者的上下文可以和给实现者的完全不同。

主 agent 在源码里就叫 Steve，带着完整会话历史从 phase 1 一路干到 phase 7，每阶段结束立即 commit 并开出或更新 PR——这是写进每份合同的硬性条目，PR 即检查点。

审查走另一路。phase 2/3/4/6/7 结束后，编排器用 getPr 从 Steve 的 run 元数据里摸出 PR URL，再 create 一个全新的云端 agent 从该 PR checkout，提示词直接摊牌：

审查 agent 手里同样有那份阶段合同，所以它审的不只是代码质量，还有违约：phase 3 的 PR 里混进了一行实现逻辑，就是该被抓出来的东西。审查报告原文灌回 Steve：Fix the PR feedback from the phase N review。审查者与被审者零共享上下文，这是刻意的——让同一个会话里的 agent 审自己刚写的代码，多半是走过场。

phase 6 又进一步：断言不让 Steve 写，另开一个名为 phase 6: invariance 的新 agent 从当前 PR checkout 来写。写实现者不自定不变量，此之谓也。

断了怎么办

云端一个阶段动辄跑几十分钟，容错分两级。

第一级对付流断。SDK 的等待流挂掉时报 stream is no longer available，waitWithReconnect 只认这一种错误，拿 run id 调 getRun 重连同一个 run 接着等，其余错误一律照抛。run 本身还在云上跑，本地网络抖一下不该拖垮整条流水线。

第二级对付进程挂。本机进程死了什么都不丢，因为会话状态全在 Cursor 云端。--resume 列出云上 agent 供选，输入 phase 号，再选 phase 还是 review 模式，纯函数 pipelineStepsFrom 推导出剩余步骤接着跑。phase 1/5 本就没有审查步，续跑时选 review 会被 assertResumeMode 当场拒绝。

部件

流水线之外还有四个小入口，link 脚本把前三个连同 phase-7 软链成 prime-agent-* 全局命令：

kick-off：单发任务。读一句 prompt，带上常驻上下文丢给新开的 agent
review：手动对抗审查。选一个云上 agent 自动摸它的 PR，或直接贴 PR 链接
take-over：反向接力。读本机当前分支，让云端 agent「finish the work started on this branch」
get：列出云上 agent，挑一个看详情

所有入口汇到同一套底层：context.ts 出三种提示词模板，把文件全文以 <File> 块内联进 <Context>，不指望 agent 自己检索；agents.ts 封装 @cursor/sdk，模型写死 grok-4.5、effort high。方向键选择器和等待转轮都是手搓的，整个终端交互没引一个 UI 库。

边界

合同不通用。七份 phase 文档写满目标项目的私货：Odin 路径、Linear 工单流转、agent_task_finalize。编排器通用，合同得按项目重写
串行无预算。一个阶段卡住整条停，没有超时，也没有重试上限
审查只有单轮。Steve 修完反馈不复审，修没修对，靠后续阶段的审查兜底
上下文全文内联，常驻文件一大就烧 token，没有任何截断逻辑
模型硬编码在源码里，换模型要改代码
测试全押在流水线步骤推导和断流重连这两处纯逻辑上，碰网络的部分一条没测

代码是编排，合同才是方法论——这一千多行代码里真正值得抄的，是那 187 行 markdown。至于主 agent 为什么叫 Steve，源码里没有答案，我也就不替他追究了。
