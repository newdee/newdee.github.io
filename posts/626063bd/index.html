Pane as an Actor.

让终端不只是运行命令的地方，而成为可以独立运行、持续存在、相互通信和协同工作的执行单元。

一、为什么还需要一个新的终端复用工具？

如果你经常使用终端进行开发，那么 tmux 大概率是一个绕不开的工具。

它解决了一个非常实际的问题：一个终端窗口不应该只能运行一个程序。

通过 tmux，我们可以把终端拆分成多个 Pane，在不同 Pane 中运行 Shell、编辑器、编译任务、服务进程，甚至多个 AI 编程 Agent。

对于习惯终端开发的人来说，这已经是一套非常成熟的工作方式。

但随着开发工作流发生变化，终端承担的角色也在发生变化。

过去，我们在终端里主要执行的是：

  • 编译、测试和构建任务。
  • 启动 Web 服务、数据库和其他后台进程。
  • 使用 Vim、Neovim 等终端编辑器。
  • 通过 SSH 管理远程服务器。
  • 使用脚本完成自动化操作。

现在，终端中还出现了大量具有自主执行能力的程序：

  • Claude Code
  • Codex
  • Gemini CLI
  • OpenCode
  • 各种自定义 AI Agent

这些程序不再只是简单地执行一条命令。它们可能持续运行几分钟甚至几个小时，拥有自己的任务上下文，等待用户输入，也可能需要与其他 Agent 协作。

这带来了几个新的问题。

1.1 终端会话不应该依赖客户端连接

传统终端的一个问题是，终端客户端与进程之间的生命周期关系并不总是符合长期任务的需求。

例如：

  1. 在终端中启动一个 Agent。
  2. Agent 正在分析一个大型项目。
  3. 用户关闭终端窗口或者断开 SSH。
  4. 原本运行中的任务可能随之中断。

即使使用 tmux，仍然需要考虑服务器重启、Session 恢复、Pane 意外关闭等问题。

对于需要长时间运行的任务，仅仅做到 detach 并不够。

我们希望的是：

  • 客户端关闭，任务仍然运行。
  • 重新打开终端，可以恢复之前的工作环境。
  • 意外关闭 Pane，可以在一定时间内撤销。
  • 程序更新时，可以迁移正在运行的 Session。

1.2 多个 Agent 之间缺少统一的通信机制

假设我们同时运行三个 Agent：

  • Architect：负责分析需求和制定方案。
  • Developer：负责代码实现。
  • Tester：负责执行测试和验证结果。

在传统的终端工作流中，它们虽然可以分别运行在三个 Pane 中，但这三个 Pane 本质上只是三个独立的终端。

它们之间并没有天然的通信关系。

一个 Agent 如何知道另一个 Agent 是否空闲？

如何向指定 Agent 发送任务？

如果接收方正在执行其他任务，消息应该怎么办？

如何知道一条消息最终有没有被处理？

如何追踪任务从一个 Agent 传递到另一个 Agent 的过程？

当然，可以通过文件、共享目录、Socket 或者外部消息队列实现，但这意味着开发者需要额外建设一套通信基础设施。

1.3 终端缺少统一的运行状态管理

当终端中运行的程序越来越多，仅仅通过切换 Pane 已经不够用了。

我们还需要知道：

  • 哪些 Pane 正在运行？
  • 哪些 Pane 当前处于空闲状态？
  • 哪些 Agent 正在处理任务？
  • 哪些消息还在 Inbox 中等待处理？
  • 哪些任务已经完成？
  • 某个 Pane 最近执行了什么操作？
  • 某个 Agent 当前到底在做什么？

这已经不只是终端布局的问题，而是一个运行时管理问题。

Keepane 就是围绕这些问题设计的。

二、Keepane 是什么？

Keepane 是一个使用 Rust 开发的跨平台终端复用工具。

它保留了 tmux 的核心使用方式，同时在传统终端复用能力之上，增加了持久化运行、Pane 生命周期管理、消息通信、任务追踪、Agent 集成和远程管理等能力。

项目采用的核心设计理念是：

Pane as an Actor。

可以把每一个 Pane 理解成一个独立的执行单元。

一个 Pane 不只是屏幕上的一个矩形区域，它还拥有：

  • 独立的进程和终端环境。
  • 自己的名称和地址。
  • 独立的工作模式。
  • 自己的消息收件箱。
  • 当前运行状态。
  • 与任务相关的事件记录。

人、Shell、脚本和 AI Agent 都可以通过统一的消息机制与 Pane 交互。

这里需要明确一个边界：

Keepane 不负责 LLM 推理，不负责 Agent 的规划，也不负责决定多个 Agent 应该如何分工。

它负责的是更底层的事情：

管理执行环境、维护运行状态、传递消息，以及让这些执行单元能够被观察和控制。

从架构上看，它更接近一个本地终端执行环境与 Agent 协作基础设施。

三、整体架构设计

Keepane 的架构可以分成几个主要部分：

  1. Client：命令行客户端。
  2. Server：后台运行时服务。
  3. Session / Window / Pane：终端资源组织结构。
  4. Mailbox：消息收发与队列管理。
  5. Task & Event Log：任务关联和事件记录。
  6. Dashboard：统一状态观察与交互控制。
  7. MCP Integration：为外部 AI Agent 提供工具接口。
  8. Remote Link：跨机器通信与远程 Pane 管理。

Keepane 采用 Client / Server 架构。

Server 负责管理所有 Session、Window、Pane 和相关运行状态。

Client 则主要负责接收用户输入、向 Server 发送命令，以及展示终端画面。

这种设计有几个重要好处：

第一，进程生命周期与终端客户端解耦。

客户端退出，不意味着 Server 退出，更不意味着 Pane 中运行的程序必须退出。

第二，多个客户端可以访问同一个运行环境。

例如，可以在不同终端窗口中连接同一个 Session，也可以通过远程 Web 页面查看运行状态。

第三，管理接口与终端展示分离。

CLI、Dashboard、MCP 和 Web 管理界面可以共享同一套运行时管理能力，而不需要各自维护一份 Pane 状态。

3.2 Session / Window / Pane

Keepane 保留了 tmux 熟悉的三级组织结构：

Session 是一组工作环境。

Window 是 Session 中的工作窗口。

Pane 则是真正承载进程的终端执行单元。

这种组织方式可以兼顾传统终端用户的使用习惯，也能为后续的自动化管理提供清晰的资源层级。

四、底层终端实现：Keepane 如何管理真正的终端进程？

终端复用工具最核心的工作，并不是简单地把一个屏幕分割成多个区域。

真正困难的是：如何在后台管理多个独立运行的终端进程，并将它们的输出正确地组合成用户看到的终端画面。

Keepane 的底层实现主要涉及 PTY、终端状态解析、屏幕渲染以及跨平台输入输出处理。

4.1 每个 Pane 都拥有独立的伪终端

PTY（Pseudo Terminal，伪终端）是终端复用工具的基础。

普通 Shell 进程需要一个终端设备来完成输入和输出。

如果要同时运行多个 Shell，就需要为它们提供独立的终端环境。

Keepane 为每个 Pane 创建独立的 PTY：

它可以读取键盘输入、输出 ANSI 控制序列、修改光标位置、切换颜色以及进入 Alternate Screen。

这意味着 Vim、htop、Claude Code 等交互式程序不需要知道自己正在被 Keepane 管理。

4.2 Windows 与 Unix 的终端差异

跨平台终端实现并不简单。

Windows 和 Unix 系统的终端模型存在明显差异。

在 Linux 和 macOS 上，Keepane 使用 Unix PTY。

在 Windows 上，则使用 ConPTY（Console Pseudo Terminal）。

ConPTY 是 Windows 提供的伪终端接口，能够让终端宿主程序与命令行进程之间通过输入输出流交互。

Windows 的输入处理尤其值得关注。

传统 Windows 控制台并不完全等同于 Unix 终端的字节流模型。

Keepane 在 Windows 上利用原生 Win32 输入模式传递按键事件，以兼容 PowerShell、PSReadLine、IME 输入以及 WSL 中的交互式程序。

在 Linux 和 macOS 上，则处理终端发送的按键序列，包括修饰键、Bracketed Paste 和 SGR Mouse 等。

这类细节直接决定了终端复用工具能否真正兼容日常开发工具，而不仅仅是能启动一个 Shell。

Server 将各 Pane 的屏幕状态组合成一个完整的 Window 画面。

客户端并不需要直接管理所有子进程的终端状态。

主循环有 16 毫秒的帧率上限。4 个 Pane 满速刷屏、挂着一个客户端时，服务端 CPU 占用在一个核以内；同样负载下去掉这个上限是 166% 核。按键仍然立刻画出来，不增加打字延迟。

4.4 进程树与资源清理

终端复用工具还需要处理一个容易被忽略的问题：

如果用户关闭 Pane，里面启动的程序是否也应该退出？

答案通常是肯定的。

否则很容易留下孤儿进程。

Keepane 在 Windows 上使用 Job Object 管理 Pane 的进程树，并配置关闭时终止整个进程组。

在 Linux 和 macOS 上，则通过对应的进程组与终端生命周期管理完成清理。

因此，关闭 Pane、Session 或 Server 时，可以将其管理的整个进程树一起终止。

这对于长期运行多个 Agent 尤其重要。

六、核心设计：Pane as an Actor

这是 Keepane 与传统终端复用工具之间最值得关注的设计方向。

在 Actor Model（Actor 模型）中，系统由多个相互独立的 Actor 构成。

每个 Actor：

  • 拥有自己的内部状态。
  • 可以接收消息。
  • 可以向其他 Actor 发送消息。
  • 可以独立处理任务。
  • 不需要直接访问其他 Actor 的内部状态。

Keepane 并不是一个完整的 Actor Model 运行时，但它借鉴了这种组织思想。

每个 Pane 都拥有独立的身份、工作模式、Inbox 和运行状态。

例如：

三个 Pane 可以分别运行不同的 Agent。

它们不需要共享同一个终端，也不需要通过直接操作彼此的进程来完成协作。

它们只需要通过 Keepane 提供的消息接口进行交互。

6.2 Work Mode：Pane 的工作模式

不是所有 Pane 都应该自动执行收到的消息。

例如：

  • Shell 可以在命令提示符空闲时执行收到的命令。
  • AI Agent 应该在当前一轮任务完成后再接收下一条消息。
  • 普通交互程序则应该由程序自身读取消息。

Keepane 通过 Work Mode 区分这些行为。

模式空闲判断消息处理方式
normal不自动判定就绪消息进入 Inbox，由程序读取
shellShell 回到命令提示符自动输入并执行命令
aiAgent 触发结束回合 Hook自动将消息作为下一轮 Prompt 输入

这背后有一个非常重要的设计原则：

消息到达不代表消息应该立即执行。

如果一个 Agent 还在处理任务，直接把新消息注入它的终端，可能破坏当前执行过程。

因此，Keepane 将消息接收和消息交付分成两个阶段。

Pane 此刻的状态用一个词表示（#{pane_state}，Dashboard 和手机页面上也会显示）：idle 空闲、busy 正在执行、typing 有人按过键但还没回车、no-agent 表示 ai 模式的 Pane 回到了 Shell 提示符、unknown 表示 shell 模式的 Pane 从未发出过提示符标记（例如 cmd）、exited 表示程序已退出。用户正在输入时，消息会等着，不会插进正在写的那一行。

7.1 消息信封

Keepane 的消息并不是简单的字符串。

每条消息都有固定格式的 Envelope（消息信封）。

其中包括：

  • Message ID。
  • Sender。
  • Recipient。
  • Sender Name。
  • Sender Mode。
  • Task ID。
  • Reply Reference。
  • Hop 信息。
  • Via 信息。
  • Message Content。

发送方主要提供目标 Pane、回复关系、任务关联和消息内容。

其余身份及路由字段由 Keepane 填充。

这样可以避免发送方随意伪造消息来源，并为消息追踪提供可靠依据。

对 Claude Code、Codex 和 pi，即使没有装 Hook，Keepane 也能从它们的会话记录里看出一轮已经结束，最多晚三秒把 Pane 设为空闲；装了 Hook 就是立刻生效。

八、群聊：让多个 Agent 在一个频道里说话

一条消息只进一个 Inbox。三四个 Agent 做同一件事时，这种一对一的传话很快就不够用：谁说过哪一句、谁该接着说，全靠派活的那个 Pane 自己记。

因此 Keepane 增加了频道（Channel）。每个 Agent 用一个称呼和角色加入频道，说自己要说的话，想看的时候自己读。

上面这张截图是一个真实的频道：UnifyTerm 和 Keepane 的两个 Agent 在里面商量怎样让 UnifyTerm 的命令在 Keepane 的 Pane 里可用，中间由人插话确认版本。

8.1 默认不推送

这是群聊最重要的一个设计取舍。

说出来的话留在频道里，不会进入任何人的 Inbox。

如果每句话都推送给所有成员，那么一个有 5 个 Agent 的频道里，每条消息会进入 4 个 Agent 的上下文，token 成倍消耗；而且 Agent 收到消息就倾向于回复，很容易互相回个不停。

因此交付规则是：

情况行为
普通发言只进频道，成员想看时自己 chat read
被 @称呼 点名立刻收到一条 Inbox 消息，附带它上次读完之后频道里的发言（最多 20 句）
加入时写了 --hear all每句都收到，2 秒内的几句合并成一条
成员处于 shell 模式不推送，因为消息在那里会被当成命令执行；发言者会收到说明

被点名的消息附带上下文，是因为只推一句话时，Agent 并不知道前面在讨论什么。

8.2 身份由服务端盖章

成员能自己决定的只有称呼和角色。

机器、session:窗口.pane、Pane 编号和名字、Agent 种类、模型这些字段由 Keepane 盖章，记在成员上，也记在它说的每一句话上。

因此一个 Pane 只能以自己的身份加入和发言，不能冒充另一个 Pane。

人在所有 Pane 之外（Dashboard、自己的终端、C-b :）发言时，身份是 you@<机器名>，不需要加入。

8.3 成员比 Pane 活得久

Pane 关掉或者 Server 重启之后，成员仍然留在频道里，只是变成离线状态，频道里会写一句。

同名的 Pane 回来（恢复 Session 会恢复 Pane 名），或者任意 Pane 用它的称呼重新加入时，它重新在线，并接着从原来读到的位置继续读。

主动离开或者被移出的成员标记为"已离开"：不计入成员数，@ 它会返回一条未送达的说明，同名 Pane 回来也不会自动接回。

频道保存在事件日志旁边，每个频道一天一个 JSONL 文件，默认保留 30 天。同样这几个操作也是 MCP 工具，所以 Agent 可以直接通过工具调用加入和发言。

9.3 Agent 的用量与花费

除了消息层面的追踪，Keepane 还会读取 Agent 自己写的会话记录。

花费的口径需要说明：pi 自己记录了花费，直接采用；其余按 LiteLLM 的公开价目表给每个模型的新输入、读缓存、写缓存和输出分别计价。价目表是各家 API 的标价，而使用订阅（Claude Max、ChatGPT Pro）时实际计费方式不同，因此这个数字的含义是"同样的工作走 API 要花多少"。价目表里没有的模型不计价，数字后面带一个 +。

9.4 Agent 一步步在做什么

同一份会话记录里也记录了每一步的起止时间。Dashboard 右侧按 T 切到 Trace 标签页，会把所选 Pane 的 Agent 画成瀑布图，每 2 秒刷新一次。

每种步骤一种颜色：模型品红，读取和搜索青色，修改文件黄色，运行命令蓝色，子 Agent 绿色。失败的步骤标红并加 ✗，会话记录里写明原因的会一并显示（被用户拒绝是 denied，被 Hook 拦下是 hook: …）；仍在进行的加粗，末尾有 ▶。

最上面两行是实际使用中最有价值的部分：Agent 正在等你做什么（等权限、等回答），以及仍在后台运行的任务。同一种已结束的步骤连续三步以上会折叠成一行，后面标 +N（依次执行）或 ×N（同时发出）。

对应的命令行工具是 keepane trace-pane -t <pane>，-J 输出 JSON。

例如：

12.1 两档权限

配对之后双方还看不到任何东西。规则只有一条：谁的 Pane 被看，就在谁那台机器上设置。

远程机器发来的消息默认只允许进入 Agent Pane。

如果需要让远程机器控制本机 Shell，则需要显式授权（--full）。

这项限制非常重要。

因为远程命令执行与远程 Agent 通信具有不同的安全风险。

普通 HTTP 在局域网里可以被抓包，所以 --full 默认只对 Tailscale 地址和本机生效；确实需要在局域网里使用时要写明 --full --lan。共享和授权都只能在 Pane 之外执行，否则 Agent 就可以自己把别的机器放进来。

12.2 远程 Session 与远程 Pane

给了本机 --full 的机器，它的 Session 可以直接在这边使用。

它们仍然属于那台机器，只列在那台机器名下：C-b w 的结构图里每台机器一个框，C-b v 按机器分组。按 Enter 进去之后，查看、输入、快捷键、主题和复制模式都用本机的；在这边对它分屏、关闭、调整大小、缩放和改名，都交给对方机器执行，完成后显示在这边。

还有两条更轻量的方式：

命令作用
keepane link watch <地址>/%worker在任意终端里实时查看对方的一个 Pane
keepane link attach <地址> work整个进入对方的 Session，状态栏和前缀键都是对方的，按 F12 把按键交回本机
keepane link start <地址> -n helper -- claude在对方机器上创建 Pane，受对方的白名单和数量限制

12.3 连接与权限是两件事

这两件事现在分开管理，各自只管自己这一边：

  • link disconnect：本机不再向对方发起请求，它的 Session 从这边消失；对方在本机的权限不变，link connect 恢复。
  • link allow --none：收回对方在本机的全部权限，配对关系仍在。
  • link remove：解除配对，两边一起删除。

所以不想看某台机器就断开它，想挡住它就收回权限。

13.2 在飞书里回复 Pane

普通 HTTP 页面无法发送系统通知，锁屏之后浏览器会把页面暂停。因此如果希望锁着屏也能收到并回复，可以接入飞书（Lark 同样可用）。

长连接由 Keepane 主动连向飞书，本机不对外开放任何端口，也不需要公网地址。

场景行为
回复"在等你"的通知回复立刻送进 Pane。单个键按原样按下（1、y、esc、enter），其他文字先输入再回车
回复其他通知作为一条消息发给那个 Pane，与 send-message 一致
命令/panes、/to <pane> <文字>、/key <pane> <按键>、/screen <pane>

只接受白名单中的账号，并且只处理与机器人的单聊。默认权限很窄：按键只发给 Agent，消息只发给 Agent 和 normal 模式的 Pane。让没有 Agent 的 Pane 接收按键、或者让 shell 模式的 Pane 接收消息，都等于执行命令，因此需要单独的 --shell 授权；/screen 会把屏幕内容传到飞书服务器，需要 --screen。这些授权只能在 Pane 之外执行。

Keepane 支持通过插件扩展命令和行为。

插件可以由一个 .keepane 文件及其所需脚本组成。

脚本可以使用不同语言，通过 Keepane CLI 与 Server 交互。

插件系统还提供 Hook、菜单、Popup、任务列表、文本搜索以及终端录制等能力。

这使 Keepane 不只是一个固定功能的终端复用程序，也具备了可扩展性。

十七、Keepane 与 tmux 的区别

如果只从终端分割和 Session 管理来看，Keepane 与 tmux 有很多相似之处。

但两者的设计重点并不完全相同。

维度tmuxKeepane
终端复用支持支持
Session / Window / Pane支持支持
后台运行支持支持
配置语法原生配置体系兼容部分 tmux 配置语法
跨平台Unix 系统为主Windows、Linux、macOS
Session 恢复需要额外工具或方案内置保存与恢复
Pane 撤销关闭不属于核心能力支持短时间撤销
Pane 命名支持支持

这里并不是说 Keepane 要完全取代 tmux。

tmux 已经有成熟的用户群体、插件生态和长期积累的使用习惯。

Keepane 更关注的是：当终端中运行的程序从简单命令逐渐演变为长期运行的 Agent 时，终端基础设施应该具备哪些新的能力。

十八、Keepane 的设计边界

一个基础设施项目是否可靠，不仅取决于它能做什么，还取决于它明确不做什么。

Keepane 有几个值得明确的设计边界。

18.1 不负责 Agent 的智能决策

Keepane 不负责：

  • LLM 推理。
  • Prompt Engineering。
  • Agent 规划。
  • 模型选择。
  • 模型调用。
  • 复杂的多 Agent 决策策略。

这些工作应该由上层 Agent Framework 或 Agent 本身负责。

Keepane 只管理执行环境与协作通道。

18.2 消息交付不等于任务完成

消息进入 Inbox，不代表任务已经执行。

消息成功交付，也不代表接收方一定完成了任务。

因此，消息状态、执行状态和任务状态需要分别理解。

Keepane 提供追踪能力，但不能把一条消息的 Delivered 状态直接等同于业务任务的 Success 状态。

18.3 终端恢复不等于程序状态恢复

Keepane 可以恢复终端布局、启动命令、目录和历史内容。

但它不能保证恢复任意程序的内存状态。

如果 Agent 自己不支持会话恢复，那么机器重启后仍然需要重新启动 Agent。

18.4 本地管理不等于完整安全隔离

Pane 是独立的执行环境，但不是安全沙箱。

多个 Pane 通常仍然运行在同一用户的操作系统权限下。

因此，Work Mode、Agent 命令白名单和 Pane 数量限制可以降低误操作风险，但不能替代容器隔离、操作系统权限隔离和完整的安全策略。

这一点在构建自动化执行系统时尤其重要。

18.5 仍然没有做的

  • Linux 和 macOS 上还没有 keepane update，只提示升级方式。
  • shell 模式依赖提示符钩子，所以 cmd 和 sh 暂时不会自动接收消息，只能用 read-message 读取。
  • 其他机器的 Pane 还不能加入群聊。
  • Dashboard 里的任务和事件还没有搬到手机页面上。
  • 群聊在宣布稳定之前仍属于实验性功能，兼容性承诺见仓库的 docs/compatibility.md。

十九、总结：终端正在从交互界面演变为执行基础设施

回头看终端工具的发展：

最初，我们需要的是一个 Shell。

后来，我们需要 tmux 这样的终端复用工具，以便同时管理多个工作环境。

现在，随着 AI Agent 开始进入日常开发工作流，终端又出现了新的需求：

  • 执行环境需要长期存在。
  • 多个执行单元需要拥有独立身份。
  • 任务需要在执行单元之间传递。
  • 消息需要排队和追踪。
  • 运行状态需要统一观察。
  • Agent 需要能够通过标准工具接口管理自己的工作环境。
  • 多台机器上的执行环境需要能够互相连接。

Keepane 尝试解决的就是这些问题。

它并没有试图重新设计一个 Agent Framework，也没有试图把所有 AI 能力都放进终端复用工具中。

相反，它选择从更基础的执行环境入手：

让每一个 Pane 成为一个可以独立运行、持续存在、接收消息、反馈状态的执行单元。

当 Pane 具备了身份、状态、Inbox 和生命周期管理能力之后，传统终端复用工具就有机会进一步演变为一个本地 Agent 协作工作台。

这也是 Keepane 的核心设计理念：

Pane as an Actor.

终端不只是程序运行的地方，也可以成为组织程序、管理任务和连接 Agent 的基础设施。
