OpenViking：把 agent 的上下文做成一个文件系统

2026-08-19 ·笔记 ·5199 字 ·约 13 分钟 ·阅读 次
Agent架构PythonRust

OpenViking 是火山引擎开源的 agent 上下文数据库。它的主张一句话就能说清：别让 agent 去查一个黑盒向量库，让它像开发者一样用 ls、tree、find 翻自己的上下文。
记忆、资源、技能统一挂在 viking:// 这个虚拟文件系统下，每个目录带着 L0 摘要和 L1 概览，检索先定位到目录再往下钻，每一次查询都留下可回看的路径。
读完之后我最认可的不是那套三层结构，是它在一致性模型里写下的那句话：宁可漏掉一条搜索结果，也不要返回一条错的。 整个写入路径的所有顺序决定，都是从这一句推出来的。

先说规模和技术栈

它不是个薄封装。到今天的 HEAD（afa5aae9），2026-01-29 起 2,033 次提交，三种语言各管一层：

层语言规模
服务与业务逻辑Pythonopenviking/ 619 个文件、148,477 行
文件层 RAGFSRustcrates/ragfs/ 78 个文件、40,673 行
向量与标量索引引擎C++src/ 65 个文件、12,260 行

C++ 那层自带依赖（croaring 位图、leveldb、rapidjson、spdlog），是真的在写索引引擎而不是调库。协议是 AGPLv3，crates/ov_cli 和 examples/ 单独给 Apache 2.0。背后有论文：VikingMem，arXiv:2605.29640，VLDB 2026 收录，README 说开源的是其中一个子集。

viking://：三种上下文，一棵树

它把上下文按人的认知习惯切成三类，各有不同的生命周期和谁来发起：

  • Resource——外部知识与规则，长期、相对静态，用户主动加（文档、手册、代码仓）。
  • Memory——agent 的认知，长期、持续更新，agent 自己记。
  • Skill——可声明的能力配置，长期、静态，用户或系统加。

三类挂在同一棵树上：

内置的记忆类型有九种，各有默认落点：profile.md（基本信息）、preferences/（按主题分的偏好）、entities/（人、项目、组织）、events/（决定与里程碑）、identity.md（助手的名字、人格）、soul.md（原则、边界、风格）、以及给「agent 进化」用的 cases/、trajectories/、experiences/。应用可以自定义类型。

peers/ 这个设计我第一次见：如果对话里出现了一个稳定的第三方，关于他的记忆写进他自己的空间，而不是糊在当前用户的记忆里。路由规则写得很死——只有在归档批次里真实出现过的、通过安全校验的 peer_id 才允许写入，不在白名单里的直接跳过；某些 schema（比如 cases）标了 peer_enabled: false，就完全忽略 peer 目标，只写自己。执行派生的那三类（trajectories/experiences 和可执行技能）永远不写 peer 记忆。

三层不是每个文件一份

这是 README 容易让人误会、而文档说得很准的一处。L0/L1 是目录级的语义挂件，不是每个文件配一份：

层落点默认正文上限用途
L0 摘要目录里的 .abstract.md256 字符向量检索、快速筛
L1 概览目录里的 .overview.md4000 字符rerank、内容导航
L2 详情原始文件与子目录无统一上限按需加载全文

普通文件不会各自生成 L0/L1，文件摘要只作为输入汇进所属目录的 L1。而 L0 又是从 L1 正文里截出来的——具体是 H1 标题之后、第一个 ## 之前的那段简述。生成方向是自底向上：文件摘要 → 叶子目录 L1 → 叶子 L0 → 父目录，一直冒到命名空间边界。

新版 L0/L1 用一种叫 OKF 的最小格式：YAML frontmatter 加可见正文。frontmatter 里最有意思的是 freshness 那组字段，它统计的是直接子项而不是整个递归子树：

直接子项超过 semantic.sidecar_sample_size（默认 32）就走确定性、保序的稳定采样——同一棵没变的树反复刷新会选中同一批样本，避免正文被无意义地重写、避免 git diff 里全是噪声。pending_child_changes > 0 的含义被写清楚了：正文仍然可读，但已知落后于底层变化。

而且它对自己没做完的部分很坦白，文档里挂着一个 TODO：

当前实现在每一个成功的 resource/skill 语义任务后都尝试向上冒泡，即使新生成的子摘要没有变化。这不是最终的调度策略。未来的实现应该用 freshness 来合并、设阈值或加时间窗……目标是减少热目录上的重复刷新和向上的写放大。

写放大这个问题是真的：一个深目录里改一个文件，会一路把每一层父目录的摘要都重刷一遍。承认它比藏起来好。

读取面的行为也分得很细：abstract()/overview()、find 与 rerank 的预览、ls output=agent 都只给正文；只有直接 read(".../.abstract.md") 才拿到 frontmatter；普通 ls 把这两个挂件藏起来。做嵌入时元数据有白名单，初始只放 directory 一个字段进去——source、generated_by、freshness 全部排除，并且明确写了「正常向量化和管理员 vectors_only 重建索引用同一套策略，所以重建索引不会改变检索输入」。这条对可复现很关键：重建索引之后检索结果不该变，这是个容易被破坏的不变量。

写保护也是同一个思路：公开 write/batch_write 能改 L0/L1 的正文，但挂件必须已存在（公开接口不能凭空造一个 .abstract.md），只给正文的请求会继承已存的元数据，给完整 OKF 的请求必须保留所有已知元数据、改一个受保护字段就失败，append 只追加正文永不碰 frontmatter。而且正文更新之后只重建当前存在的那些层、不重新生成语义——不然你刚手写的正文会被后台摘要盖掉。

检索：树是用来导航的，不是用来打分的

检索分两条入口，差别是要不要过模型：

find()search()
需要会话上下文不需要需要
意图分析无LLM 分析
查询数量单条0–5 条 TypedQuery
延迟低较高

意图分析这一步吃的是「会话压缩摘要 + 最近 5 条消息 + 当前查询」，产出 0 到 5 条带类型的查询。0 条也是合法输出——闲聊和寒暄不需要检索。三类查询还各有文体约定：skill 用动词开头（「创建 RFC 文档」），resource 用名词短语（「RFC 文档模板」），memory 用「用户的 XX」（「用户的代码风格偏好」）。这种约定看起来土，但它让 embedding 的输入分布和被检索的内容对齐了，比堆 prompt 有用。

分层检索用优先队列递归下钻，每轮并行展开最多 4 个目录，收敛判定是 top-k 连续 3 轮不变（或候选池连续 3 轮不长）就停。

所以默认行为其实是：树负责导航和上下文完整性，最终排序纯粹是每个节点自己的语义分数（有 rerank 就加一层 rerank）。这不是 bug——配置文档把 1.0 ignores the parent score 写得明明白白——但它和「目录递归检索」这个宣传语给人的印象不太一样：你可能以为父目录的相关性会抬高子文件的排名，默认并不会。想要那个行为，得自己把 alpha 调到 0.5 之类。

顺带记几个常量，调参时有用：GLOBAL_SEARCH_TOPK = 10（全局定位起点的候选数）、MAX_CONVERGENCE_ROUNDS = 3、MAX_PARALLEL_CHILD_SEARCHES = 4、MAX_RELATIONS = 5、DIRECTORY_DOMINANCE_RATIO = 1.2。rerank 只在配了 AK/SK 且处于 THINKING 模式时启用，返回非法结果或 API 失败就退回向量分数——这个降级是对的，rerank 是精度优化而不是正确性依赖。

一致性：所有顺序都是从一句话推出来的

09-transaction.md 是这个仓库最值得读的一篇。它开头就把立场摆出来：

OpenViking 是一个上下文数据库，FS 是真相源，VectorDB 是派生索引。丢掉的索引可以从源数据重建，丢掉的源数据无法恢复。因此：

宁可漏掉一条搜索结果，也不要返回一条错的。

然后每个操作的步骤顺序都是这句话的推论：

  • rm——先删索引，再删文件。反过来的话，文件没了索引还在，搜索会返回一个不存在的文件。按这个顺序，中间崩了最坏情况是「文件还在但搜不到」，重试能补完。
  • mv——先拷贝到新位置（源还完整，安全），再改向量库里的 URI，最后删源。改索引失败就把拷贝清掉，源和旧索引都完好。
  • add_resource——先在最终路径上拿子树锁，语义处理跑在临时目录上，完成后同步进最终位置。这期间任何 rm 想拿同一路径的子树锁都会拿到 ResourceBusyError。

锁的设计也很朴素，就两种类型：EXACT（锁一个具体路径）和 TREE（逻辑上覆盖整个子树，但只在根上写一个锁文件）。锁文件的内容是栅栏令牌 {handle_id}:{time_ns}:{lock_type}。

几个我觉得写得好的地方：

TOCTOU 双检 + 让后来者退让。 写完锁文件之后再扫一遍祖先和子孙，发现冲突就比较 (时间戳, handle_id)，较晚的那个撤掉自己的锁，等一会再试。这是防活锁——如果双方都固执重试，就都进不去；定一个全序让后来者退，就总有一个能走。

等待超时固定为 0。 这条我一开始以为是没做完，读下去发现是刻意的：运行期等待超时被固定成 0.0 并且不再接受外部配置，抢不到锁就直接 LockAcquisitionError。不排队意味着不会有调用方被莫名堵住，冲突立刻暴露给上层去决定重试还是报错。配套的是三层过期清理：锁文件里的令牌时间戳超过 lock_expire（默认 30 秒）就在下次获取时被当残锁删掉；LockManager 每 60 秒扫一遍还持有锁但已不活跃的 handle 强制释放；进程崩溃留下的孤儿锁靠同一套残锁检测收掉。长任务不靠调大超时，而是开一个刷新循环，每 lock_expire/2 刷一次令牌。

模型调用一律在锁外。 理由写得很直接：LLM 调用延迟不可预测（5 秒到 60 秒以上），不能待在持锁操作里。所以 session.commit() 被拆成两段——

Phase 1 不加锁的依据是「不完整的归档没有副作用」；Phase 2 不再用独立 redo log，而是靠一个持久化的 session_commit 队列（QueueFS 用 SQLite 落盘），重启后 QueueManager 接着跑剩下的活。这条成立的前提被单独点了出来：记忆抽取是幂等的——从同一份归档重复抽取产出相同结果。没有这条，重放就是危险的。

并发刷同一个目录摘要用的是 coalesce_version：同一个 dirty key 上可能起多个刷新任务，但只有最新版本允许写回，过期任务在写回前把自己的结果丢掉；最后落盘时对 .abstract.md/.overview.md 短暂拿一下 EXACT 锁。这样并发改 docs/a.md、docs/b.md、docs/c.md 各持自己的 EXACT 锁互不阻塞，不需要为了刷一次目录摘要去锁整棵子树。

会话如何变成记忆

commit() 的第二段里，记忆抽取的流程是四步：

判重的决策粒度分两级，这个设计比常见的「相似度超过阈值就合并」细得多：

  • 对候选：skip（重复，什么都不做）/ create（创建，可以先删掉冲突的旧记忆）/ none（不创建，但用下面的条目级决策去处理已有记忆）
  • 对每条已有记忆：merge（把候选内容并进去）/ delete（删掉这条冲突的）

也就是说一次抽取可以同时表达「这条新的不要，但把旧的那两条合并成一条、再删掉第三条」。代价是判重要过一次 LLM，而且它有权删已有记忆。

配套的审计机制我很喜欢：每次 commit() 都往归档目录写一份 memory_diff.json，逐条记下这次的 adds / updates / deletes，updates 带 before 和 after，deletes 带被删内容全文。即使一条都没动，也会写一个全零的空 diff。 有了这个，「agent 的记忆什么时候被谁改成了什么」是可查、可回滚的——这是绝大多数记忆层缺的东西。归档目录里还有个 .done 标记文件表示 Phase 2 真的跑完了。

抽取策略由 memory_policy 控制，可以只开 self 不开 peer、可以关掉每次归档的工作记忆摘要、可以用 memory_types 白名单限定只抽哪几类。有一条依赖关系值得记：experiences 会自动激活 cases 和 trajectories（整条 agent 进化流水线）；反过来如果没有 experiences，你显式写的 cases/trajectories 会被静默忽略而不报错——这个静默我不太喜欢，配置写错了不会有人告诉你。

技能里的密钥：一个软保证

13-privacy.md 讲的机制挺聪明，但我认为它的强度需要说清楚。

add_skill 的时候，OpenViking 会用 LLM 从技能正文里抽取敏感值（api_key、token、base_url 之类），把明文替换成占位符 {{ov_privacy:skill:{skill_name}:{field_name}}}，真实值存进版本化的隐私配置；读 SKILL.md 的时候自动还原。配置按 category + target_key 组织，current.json 是当前生效快照，history/version_N.json 是全量历史快照，值不变就不产生新版本，可以激活任一历史版本回滚。

好处是真的：明文不常驻在内容文件里，密钥轮换和回滚有版本可依，对调用方透明。还原时如果占位符找不到对应值，会保留占位符并追加一段 [OpenViking Privacy Notice] 说明哪些没替换、哪些配了却没被引用——排查体验做得很细。

但要看清它的边界：「哪些是敏感值」是模型判断的。 模型漏掉一个 token，那个 token 就以明文存进了 SKILL.md，而且没有任何提示——注意力都在「配了却没用上」这种无害情况上，漏抽这种有害情况反而是静默的。另外读取时的 URI 匹配是后缀匹配 /skills/{name}/SKILL.md，宽松了些。所以我会把它当成一层降低暴露面的便利设施，不当成密钥管理的边界；真正的密钥该在进入正文之前就不在那里。

基准：数字很好看，先看清是在比什么

README 的图很扎眼：LoCoMo 上 OpenClaw 从 24.20% 提到 82.08%，Hermes 从 33.38% 到 82.86%，Claude Code 从 57.21% 到 80.32%；同时输入 token 降 34.3%–91.0%，查询延迟降 58.45%–66.10%。tau2-bench 上任务成功率零售 +6.87pp、航空 +11.87pp。

先说加分的：评测脚本是真的开源出来的，在 benchmark/ 下按被测对象分目录——locomo、longmemeval、tau2、skillsbench、retrieval、RAG、vectordb_perf，而且给竞品也写了脚本（mem0、supermemory），一键跑的 shell、导入、评估、LLM 裁判打分、统计各是独立文件。甚至还提交了一份 locomo_bad_case_questions.csv，把自己答错的题记着。这个态度比只贴一张图强得多。

再说该打的折扣，两条：

一是打分靠 LLM 裁判（judge.py），所以绝对数值取决于裁判模型和判分 prompt，跨报告横比意义有限。二是**「原生记忆 vs 接上 OpenViking」比的是集成后的端到端效果**，不是记忆算法的同条件对照——基线里 agent 用的是自己那套简易记忆，提升里既有检索质量的贡献，也有「本来几乎没有长期记忆」的贡献。24% → 82% 这种跨度，主要说明的是基线薄，而不是 OpenViking 强了 3.4 倍。反而 Claude Code 那条（57.21% → 80.32%，基线本身就不弱）更有参考价值。

我全仓库搜过。third_party/ 下只有 croaring、krl、leveldb-1.23、rapidjson、spdlog——没有 agfs；而 RAGFS_IMPL 这个字符串在整个仓库里只出现在 ORIGIN.md 自己那三行里，没有任何代码读它。也就是说那个「回退到 Go 实现」的开关是纯文档，Go 实现已经不在仓库里了。这不影响使用（Rust 实现就是唯一实现），但如果你照着 ORIGIN.md 去设那个环境变量，会得到一个什么都不做的环境变量。

相比之下 docs/en/concepts/ 那一批的准确度不错——我抽查的 score_propagation_alpha = 1.0、hotness_alpha = 0.0、MAX_CONVERGENCE_ROUNDS = 3、GLOBAL_SEARCH_TOPK = 10、L0/L1 上限 256/4000 字符、采样阈值 32、锁过期 30 秒，都和代码对得上，而且好几处主动标注了「当前实现如此，未来会改」。docs/design/ 下还有十九份 RFC（memory-link-design.md 有 96 KB），是比 README 有用得多的一手材料。

一点判断

它真正的赌注是「结构化导航优于扁平检索」。 不是「加了向量库」，向量库谁都有；是把上下文强行组织成一棵带层级摘要的树，让检索变成一次可解释的下钻。收益很实在：结果自带周围上下文、每次查询留下轨迹可以回看是哪条路径给出的、按需只读到需要的那一层。代价也实在：写入路径上要为每一层生成并维护摘要，还带来向上的写放大——它自己在 TODO 里承认这块的调度还没做完。

它对失败方向的取舍很清醒。 「宁可漏一条也不返回一条错的」，然后让 rm 反着删、mv 先拷再改、锁不等待直接失败、rerank 挂了退回向量分。这跟我前一篇写的 munder-difflin 里那条「读屏只能清除草稿不能发明草稿」是同一个方法论：先问判错的两个方向哪个更贵，再把不确定性全推到便宜那一侧。两个完全不相干的项目在这个点上想法一致，我倾向于认为这不是巧合。

用之前想清楚两件事。 一是 AGPLv3——服务化对外提供会触发传染条款，crates/ov_cli 和 examples/ 才是 Apache 2.0，README 里那句「开源版没有阉割、不需要激活码」是可信的，但许可证本身就是最大的那个约束。二是它现在的形态是一个要单独跑起来的服务（openviking-server，默认 1933 端口），加上 embedding、rerank、判重、意图分析、摘要好几处模型调用——这不是一个进程内的小库，是一套要运维的基础设施。想要轻的，同类里有把整个记忆层做成一个 Rust 单二进制的做法，我写过另一篇；有意思的是那个项目也把「真相在磁盘上、数据库只是派生索引」列为最大的架构决策，理由几乎一字不差。这个方向看起来正在收敛成共识。
