ai-memory：跨 CLI 的记忆与会话交接

2026-08-18 ·笔记 ·2957 字 ·约 7 分钟 ·阅读 次
AgentRust架构

ai-memory 用一个 Rust 二进制，为多个 Agent CLI 提供共享记忆、会话交接和检索。
生命周期 Hook 采集必要观测，Markdown 保存可维护的记忆页面，SQLite 保存查询与调度状态，MCP 提供调用入口。
下面按持久化、会话结束、检索和淘汰顺序说明，重点区分哪些状态可重建、哪些副作用可能重放。

要解决的问题

它把记忆沉淀成一棵 git 版本化的 markdown 树，作者管这叫 Karpathy 式的 LLM wiki：页面随时间被增量编译、就地版本化，语义知识累积，情节日志衰减。旁边一个 SQLite 索引负责检索。

Markdown 是权威数据，SQLite 负责可重建的检索视图。迁移、编辑与恢复应遵守这一主从关系。

文件与索引

作者在设计文档里把这条列为「最大的架构决策」，并列了三个选项：数据库为主、markdown 为主、数据库为主但按需导出。选的是第二个，理由四条：

备份与迁移就是 git clone 或 rsync 一个目录——这是需求里明写的；
Karpathy 那套模式本身就是磁盘上的 wiki，用导出步骤伪造会丢掉「能在 Obsidian 里直接翻」这个性质；
数据库可以从文件全量重建，损坏可恢复，反过来不行；
任何能读 ~/.ai-memory/wiki/*.md 的工具直接可用，不必先接 MCP。

代价写得也很直白：文件系统与 SQLite 之间不存在真正的跨资源事务。 所以一致性靠约束入口来保证——所有 wiki 写入必须走 Wiki::write_page、Wiki::apply_batch 或既有的销毁性辅助函数，让净化、准入、归属、回滚、索引更新绑在一起。运行期存储失败尽力回滚已落地的文件，崩溃窗口留给重新索引路径去收敛。文档里有一句给维护者的硬话：处理器不得直接写 wiki 文件。

项目选择 SQLite 以保持本地单进程部署，设计记录同时比较了外部数据库的部署、格式兼容与维护成本。这些取舍针对该项目，不能据此判定其他数据库普遍不适用。页面与链接保存在 SQL 表中，关系遍历使用递归 CTE，批量图计算再交给内存中的 petgraph。

会话与交接

CLI 生命周期事件先由 Hook 转发，服务端净化后分配 ObservationKind 并入队。会话结束时生成 sessions/<id>.md 与交接信息；配置模型后，再将摘要整理为 concepts/、decisions/、gotchas/ 等长期页面。

Hook 采集不等待完整后台处理。脚本硬超时二百毫秒，服务端接收返回 202，队列饱和返回 429。原生命令先以稳定幂等键写本地队列，会话结束时由独立、带锁的 hook-drain 继续投递，减少生命周期回调阻塞主程序的风险。

自动 handoff、结束标记和已覆盖观测计数在同一 SQLite 事务提交。重复结束事件只有在观测计数推进后才重新处理，使用单调计数而非墙钟判断。这个事务覆盖数据库状态，不代表外部文件及下游副作用都具有一次性语义。

模块职责

存储路径由 core、store、wiki 和 hooks 分层约束。ai-memory-core 定义标识符、Agent 种类、错误与纯计算净化逻辑，不执行 IO；ai-memory-hooks 将输入转换为 Sanitized<NewObservation> 后再进入存储，类型只能经 sanitize() 构造。

ai-memory-store 管理 SQLite，启动时完成迁移、开启 WAL 与外键。所有变更通过通道交给专用 OS 线程串行执行，读取使用可克隆的只读池，衰减计算也在该层。

ai-memory-wiki 处理 Markdown 的 front matter、临时文件写入、改名、fsync 与索引更新。跨项目链接 [[project:path.md]]、[[workspace/project:path.md]] 转换为带作用域的边；目标尚不存在时留待后续回填。文件与数据库仍无跨资源事务，崩溃恢复需重新索引。

ai-memory-llm 为提供方实现类型化客户端，结构化结果分别使用 Anthropic 工具调用、OpenAI 严格 JSON Schema 和 Gemini responseSchema。Gemini 适配会内联 $ref 并移除不支持的 Draft-2020-12 关键字；兼容端点可退回 json_object 或文本 JSON 提取，后者不能获得相同的生成约束。

ai-memory-consolidate 负责摄取、lint、清扫和改进。相同 SHA-256 内容可以跳过，新版本通过 supersedes 关联旧页，旧记录标为 is_latest=false，保存替代关系而非直接覆盖所有历史。

ai-memory-mcp 对外提供十八个工具并固定协议版本；ai-memory-web 在同一个 axum 服务的 /web 提供只读浏览，与 MCP 共用服务鉴权，v1 没有编辑 POST 路由。

ai-memory-workstream 只读各 CLI 原生 transcript，转换为可移植事件账本，不改写原生存储。ai-memory-cli 启动时加载一次配置、初始化 tracing 再分发；领域模块接收 &Config，不另设全局配置读取路径。

检索融合

memory_query 不是简单的全文搜索。四路候选各自出结果再用 RRF 融合：FTS5 全文、实体匹配、链接邻居、以及配了嵌入器时的向量余弦。实体索引来自 frontmatter 里那份规范的 entities 列表，索引为空时它不贡献任何候选或分数，而不是贡献噪声。

融合之后、最终截断之前，还有一个有界的权威乘子，按页面种类、tier、pinned、以及一小撮内置标签（canonical、active、source-of-truth、superseded、historical、test-fixture、do-not-answer-from）调整相关性。

文档里特意声明了这个乘子的边界：没有任何查询意图正则或硬性排除参与，它只在势均力敌时让维护过的规则、决策、流程、坑位压过情节证据，而不隐藏针对性的会话与历史命中。

命中会回写 access_count 与 last_accessed_at，这是衰减公式里的强化项。这个回写被节流到每页每分钟最多一次——一串重叠的搜索不该把写入者淹在冗余的强化写里。

记忆淘汰

四个 tier 落在同一张 pages 表上，用一个 tier 枚举列区分，而不是四张表。工作记忆随会话结束丢弃（行还留在 observations 里做取证）；情节记忆 30 天热、180 天冷，然后按分数驱逐；语义与流程记忆无限期，只能被新版本取代。

清扫分三段：过了 frontmatter 里 expires_at 的页面硬删（不管 pin 不 pin）；保留分低于冷阈值的走 wiki 层驱逐，删掉权威文件并留一个衰减墓碑；墓碑超过 hard_delete_after_days 才连同完整的版本祖先一起清掉，而且只在那次清扫解析出的工作区/项目范围内清。同路径上后来新建的页面会被保住。pinned 的页面豁免所有衰减路径，_slots/ 下的页面自动 pin。

信任与写入

记忆写入与提示拼装都需要显式标明信任边界。文档原话是，每一次 LLM 提示都把仓库文本、观测、wiki 页面和既往提案当作不可信数据而非指令；同样的显式信任边界与分隔符也加在自动注入的 handoff、项目简报和托管工作流数据包前面，当前指令与检出状态保持权威。

自动改进那条链上还有第二道闸：模型提出的 concepts/、decisions/、gotchas/、procedures/、_rules/ 修改先进一个待写审计轨迹，默认自动批准，但可以打开 require_approval 让它们停在待审；再往上还能配一个项目自备的可执行评估门，对选定前缀的提案跑 JSON 契约，不过就变成被拒候选而不是 wiki 写入。这个门默认关闭，且永远不从钩子路径触发。

实现约束

M0/M1 文档定义十五条后续里程碑共同遵守的约束，并要求相关评审引用出处：

配置只有一条读取路径，Config::load() 启动时调一次，此外任何地方不准 std::env::var（agentmemory #456 / #469）；
单写者 SQLite actor，所有写走一条 mpsc 通道到一条专用 OS 线程（cognee #2717）；
索引与数据在同一个事务里提交，不许「先返回再后台建索引」（basic-memory #763 / #578）；

三元组身份从第一天起进每一行领域数据（basic-memory #783 / #834）；
钩子是发射后不管，脚本硬超时 ≤200ms（agentmemory #221 / #143）；
隐私剥离是类型化边界（设计文档 §14）；
只用 JSON schema 结构化输出，不要 XML、不要 Instructor 式包装（agentmemory #492 / #539，cognee #2840）；

每条向量旁边反范式化存 {provider, model, dim}，不匹配就警告并忽略陈旧向量（agentmemory #469）；
销毁性操作前查活进程（basic-memory #765）；
原子文件写，watcher 按文件名前缀忽略自己的写；
数据目录默认绝对规范路径，启动时大声打印（agentmemory #303）；
不要全局单例与 lazy_static 配置（cognee #2228）；

零模型默认路径——不配任何 provider 系统照样能用；
provider 鉴权在构造 provider 之前解析完，客户端不自己读环境变量；
tracing 订阅者显式过滤自己的模块，避免反馈环（agentmemory #519）。

其中十一条列出了对应 issue，可以沿故障背景检查约束的适用范围；约束本身是否成立，还需要实现与测试支持。

边界

文件系统与 SQLite 之间没有真事务，这是选 markdown 当真相源换来的代价。运行期失败尽力回滚，崩溃窗口靠重新索引收敛。

下游效果在完成标记落地之前是 at-least-once 的。文档写得很坦白：进程在那些效果中间崩溃，可能重复一次已经应用过的效果，而不是悄悄丢掉剩下的。选了重复而不是丢失，方向是对的，但接入方得知道。

向量默认关闭，本地 ONNX 嵌入仍是未来工作。开了也要显式给 base URL、模型和维度，因为自托管引擎之间没有安全的公共默认值。

observations 表是有界的、经过净化的生命周期投影，是运维审计轨迹，不是完整的原生 transcript。想要完整记录得走 ai-memory run 那条托管工作流。

模块的职责可以独立理解，但较大的路由和服务文件增加了局部修改的阅读成本。修改前应先定位对应约束及其测试。

接入检查

接入时需要检查文件、索引、会话完成标记和下游效果各自的提交点。Markdown 与 SQLite 没有跨存储事务，崩溃后可能需要重建索引；完成标记之前的下游效果采用至少一次语义，消费方应能处理重复。

跨 CLI 共享的是整理后的记忆与交接材料，不是任意 Agent 的完整内部状态。原生 transcript、生命周期观测和长期页面的数据范围不同，排查缺失信息时要先确认它原本存在哪一层。

先做一次中断恢复，再决定把哪些记忆自动写进去。
